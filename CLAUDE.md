# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Static portfolio site for Usman Aslam: Astro 7 (static output), strict TypeScript, plain CSS, no UI framework,
hosted on GitHub Pages at https://usmanaie.github.io (the Firebase Hosting config is kept for the full security
headers). Three documents carry the project's context:

- `README.md`: setup, scripts, deploy, rollback, operations, asset provenance.
- `DECISIONS.md`: every deviation from the design export and the reasoning behind it (hero, fidelity,
  accessibility, performance, security, tooling). Read the relevant section before changing behaviour it
  covers, and add an entry when you introduce a new deviation or trade-off.
- `LAUNCH_CHECKLIST.md`: owner decisions and the Definition of Done.

## Commands

Node 22.19 (`.nvmrc`) and pnpm 12.11.

```bash
pnpm dev              # http://localhost:4321
pnpm build            # astro build -> dist/, then scripts/prune-dist.mjs and scripts/check-dist.mjs (production gate)
pnpm build:fixture    # PUBLIC_REVIEWS_FIXTURE=true -> dist-fixture/ (test-only, never deployed)
pnpm preview          # serves dist/ on :4173 with the headers from firebase.json, CSP included
pnpm lint             # eslint + stylelint + prettier --check, all with zero warnings allowed
pnpm typecheck        # astro check --minimumFailingSeverity hint (hints fail too)
pnpm test             # Vitest unit tests (happy-dom), tests/unit/
pnpm test:e2e         # Playwright, every project; build both outputs first
pnpm lhci             # Lighthouse CI budgets (lighthouserc.json)
```

Single tests:

```bash
pnpm exec vitest run tests/unit/menu.test.ts
pnpm exec vitest run -t "test name"
pnpm exec playwright test tests/e2e/hero.spec.ts --project=e2e-chromium
pnpm exec playwright test -g "test name" --project=e2e-webkit
```

Playwright projects: `e2e-{chromium,firefox,webkit}` run against `dist/` on :4173; `fixture-{browser}` run
`*.fixture.spec.ts` against `dist-fixture/` on :4174; `visual` takes Chromium screenshots of the fixture build.
Playwright starts `scripts/serve.mjs` itself (and reuses one already running locally). It serves the built files,
never the dev server, so run `pnpm build && pnpm build:fixture` after changing source and before running e2e.

On this Windows machine, application control blocks the downloaded Firefox and full Chrome. Firefox tests run
only in CI. Run Lighthouse with `CHROME_PATH` set to Playwright's `chrome-headless-shell` executable. Visual
baselines are Linux-only (`tests/visual/__screenshots__/linux/`), generated by running the CI workflow with
`update_baselines: true`. None are committed yet, so CI's visual job passes without comparing until they are.
Don't commit locally generated `win32/` screenshots.

Commits follow Conventional Commits (commitlint runs in the husky `commit-msg` hook), usually scoped by section,
e.g. `feat(projects): ...`. The `pre-commit` hook runs lint-staged.

## Architecture

**Content is separate from presentation.** All copy and data live in typed modules in `src/content/*.ts` (not
Astro content collections). Components contain no hard-coded copy. Some values are derived: years of
experience come from `CAREER_START` and the copyright year from `BUILD_DATE` (both in `site.ts`), and
`site.jobTitle` feeds the `<title>`, tagline and JSON-LD. `OWNER-CONFIRM` comments mark claims awaiting the
owner's verification, which are tracked in the launch checklist. Never invent or embellish claims, quotes or
case-study details.

**Pages.** `src/pages/index.astro` composes `components/sections/*`. `projects/[slug].astro` generates a case
study for each entry in `content/projects.ts`, and `projects/index.astro` lists them all. A project's
`featured: 1-3` places it among the home page's three rows; projects without it appear only on `/projects`.
Adding a project takes three steps:

1. Add the entry to `projects.ts`.
2. Make its illustration: write `scripts/art/<name>.html`, then run `node scripts/render-project-art.mjs <name>`,
   which writes `src/assets/projects/<name>.png`.
3. Add the new route to `PAGES` in `tests/e2e/helpers.ts`. The e2e and axe suites iterate over that list.

**Reviews are gated off.** `reviews.enabled` is false and there are no items. The section and its nav links
render only when real items exist. Consumers import from `content/reviews-source.ts`, which swaps in
`tests/fixtures/reviews.ts` when `PUBLIC_REVIEWS_FIXTURE=true`. That is how the carousel gets tested. Its styles
live in `reviews.css`, linked only when the section renders, so the hidden section adds nothing to the
render-blocking stylesheet.

**Client JavaScript has no islands or framework runtime.** An interactive component has a plain `<script>` that
imports an `init*` function from `src/scripts/*.ts`, and Astro bundles it as a module. Pure logic is exported
from those modules or from `src/lib/` so that Vitest can test it without a browser. The first-load JS budget is
30 KB Brotli; the site currently ships about 5 KB (`check-dist` prints the figure).

**CSP rules (strict, no `unsafe-inline`).** The CSP lives in `firebase.json`. `scripts/serve.mjs` mirrors it, so
e2e tests fail on any violation, and `BaseLayout` derives a `<meta>` copy from it for GitHub Pages, which cannot
send headers.

- Never emit inline `<script>` (JSON-LD data blocks are the one exception), `<style>` blocks, `style=""`
  attributes, `define:vars`, or data-URI assets.
- To pass runtime values to CSS, set custom properties through the CSSOM (`el.style.setProperty('--x', ...)`),
  as `carousel.ts`, `hero.ts` and `menu.ts` do.
- Never add third-party resources. Fonts are self-hosted; there are no CDNs or analytics.
- Never write the email address as plain text. Build `mailto:` links with `src/lib/email.ts`.

**The production gate.** `scripts/check-dist.mjs` runs as part of `pnpm build`. It fails the build on:

- inline scripts or styles
- forbidden text: placeholder copy, known typos, the plain-text email
- dead links or `#anchors`
- third-party resources
- unreferenced files in `/_astro`
- first-load JS over budget

`prune-dist.mjs` runs first and deletes the orphan artefacts Astro emits. If the gate flags something, fix the
source. Don't relax the gate.

**The hero.** It is a two-column grid, with copy beside an agent-flow stage. The 720×880 stage is scaled by one
unitless factor so that bubbles, connectors and the `offset-path` token stay aligned. The work is split across
three files:

- the hop sequence: `hero` in `src/content/site.ts`
- node geometry and spoke paths: `src/lib/hero-flow.ts`
- runtime: `src/scripts/hero.ts`, which handles the canvas head (the helmet turns, tilts and shifts and the eye
  lights glide, on springs, with no head-turn pictures), the charge mask, and `spreadSpoke`, which moves the
  right-hand participants out when the stage is wider than its design width

Unit and e2e tests enforce the flow's invariants: every hop goes through the agent, and RAG or tools run only
right after an LLM request. Animations pause when off-screen or when the tab is hidden. Reduced motion shows a
designed end-state frame, not a frozen first frame.

**Performance mechanisms that other code depends on:**

- Below-the-fold sections use `content-visibility: auto` until `scripts/ready.ts` sets `data-ready` at idle.
  In-page anchor jumps rely on this, and the only scroll offset is `scroll-padding-top` on the root.
- Heavy images go inside `<noscript data-defer>`, and `scripts/defer.ts` inserts them as the section nears the
  viewport.
- The build emits one stylesheet per page (`cssCodeSplit: false`).
- The Lighthouse budgets in `lighthouserc.json` are tight: mobile LCP ≤ 2.0 s (home ~1.8 s), CLS ≤ 0.02, and
  512 KB of page weight on `/`. On phones nothing may compete with the render-blocking stylesheet: the hero robot
  is preloaded at high priority only on desktop (DECISIONS.md, Hero image).

**Styling.** Every design value is a custom property in `src/styles/tokens.css`. Components use those tokens,
not raw values; colours inside illustration artwork are exempt. Styles are scoped Astro styles (the one exception is
`reviews.css`, see Reviews above), and the site is dark-only. Stylelint enforces BEM-style class names (`block__element--modifier`) and forbids `!important`.
`src/styles/fonts.css` is generated by `pnpm fonts`.

**Accessibility.** axe must report zero violations on every page. Inline SVG ids are namespaced (`flow-*`,
`trust-ring-*`, `cert-ring-*`, `ring-<variant>-path`), and an e2e test asserts the page has no duplicate ids. Unstyled
lists keep `role="list"` on purpose, for Safari and VoiceOver.

**Generated assets are committed.** Regenerate them with their scripts rather than editing outputs by hand:

- `pnpm fonts` and `pnpm images`
- `node scripts/render-project-art.mjs` for project illustrations
- `pnpm design:render <dir>` for references from the design export. It also overwrites three project PNGs
  (`agentic-ai`, `telehealth`, `ai-governance`) with the design's originals, so re-run
  `render-project-art.mjs` afterwards.
- `scripts/build-robot-head.mjs` for the hero robot, then `python scripts/build-head-layers.py` for the head
  layers cut from it (`robot-head-layers.webp/.json`)

The Experience and Contact agent portraits are the exception: `src/pages/art/[file].ts` builds them from
`src/lib/agent-portrait.ts` on every build, so there is no output file to commit.

`design-candidates/` is a git-ignored staging area for generated artwork awaiting review.

## Lint rules that catch people out

- ESLint forbids `TODO`, `FIXME` and `XXX` comments anywhere, and forbids `console.log` in `src/`
  (`console.warn` and `console.error` are allowed). Unused `eslint-disable` directives are errors.
- `pnpm typecheck` fails on hints, not just errors.
